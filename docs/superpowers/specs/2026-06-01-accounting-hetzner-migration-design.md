## 1. Background & Motivation

The accounting app (FastAPI + SQLite + SvelteKit, served via launchd + Caddy over Tailscale at `macbook.ancon-cliff.ts.net`) is the cash-basis **tax-of-record** system. Running it on a laptop is operationally fragile (sleep, reboots, network changes). The wealth/brokerage piece already migrated to Cloudflare (`internal.sparkry.ai/wealth`) and is stable; the user wants the *same operational stability* for accounting **without** the Python→TypeScript rewrite that a full Cloudflare port would require.

A Hetzner Linux host runs the existing Python stack verbatim. It also gives a **stable public HTTPS endpoint** — which solves the blocker that has prevented connecting Chase: Plaid OAuth banks need a publicly reachable, registered redirect URI, which a Tailscale-only laptop cannot provide.

## 4. Target Architecture

```
 books.sparkry.ai ─▶ Cloudflare Access (Google OAuth) ─▶ Cloudflare Tunnel (cloudflared on box)
                                                              │
 ubuntu-4gb-nbg1-2 (Hetzner; Tailscale for SSH/ops)           ▼
   cloudflared (systemd, root — tunnel token only, no app/DB access) ──▶ Caddy http://127.0.0.1:9000 (systemd; admin off)
   Caddy ──/api/*──▶ uvicorn 127.0.0.1:8000 (doppler run; user travis)
         ──/*──────▶ SvelteKit preview 127.0.0.1:5173 (doppler run; user travis)
   SQLite (/home/travis/accounting/data/accounting.db)   ← owner travis, mode 600
   systemd (user travis): accounting-api, accounting-dashboard,
            caddy, accounting-backup.timer, accounting-backup-restore-test.timer,
            accounting-disk-check.timer, weekly-pl-report.timer, accounting-alert@.service,
            plaid-transactions-sync.timer (installed, DISABLED until Chase connected)
   systemd (root): cloudflared.service (tunnel token only — no app secrets/DB access; resource limits via drop-in)
   Cohabits with (untouched): agentic-collab-proxy (:3100, runs as separate user `collab`), Syncthing (user travis)
 internal.sparkry.ai ◀── outbound calls via WEALTH_API_BASE + WEALTH_INTERNAL_KEY (as needed)
```

**OS-user model (load-bearing for security).** All accounting services (api, dashboard, caddy, cloudflared, backup, timers) run as **`travis`**. The agentic-collab sandbox runs as a **separate dedicated OS user `collab`** — this MUST be confirmed/enforced before cutover (REQ-HM-010). Because Linux `127.0.0.1` is host-global (loopback is shared across all users, not per-user), the separate user does NOT by itself block the sandbox from TCP-connecting to `127.0.0.1:8000`/`:5173`. Two controls close that hole: (1) a mandatory `API_KEY` on the app (§7), and (2) a UID-scoped local firewall rule (§7). The separate user DOES protect the DB file (mode 600, owner `travis`) and the uvicorn process environment (`/proc/<pid>/environ` is readable only by the owning UID), so secrets injected by `doppler run` are not readable by `collab`.

Ports 8000/5173/9000 are loopback-only on the box; 3100 is taken by collab (untouched). No app port is published publicly. **Caddy's app reverse-proxy listener is `127.0.0.1:9000`, NOT `:2019`** — Caddy's built-in admin API owns `127.0.0.1:2019` by default, so binding the app there collides with the admin endpoint. The Caddyfile additionally sets `admin off` (Phase 3) since the admin API is unused here; the `:9000` choice + `admin off` together remove any ambiguity. cloudflared ingress points at `http://127.0.0.1:9000`.

**Security-control sequencing (load-bearing — do NOT defer to Phase 5).** The following controls MUST be implemented and verified in **Phase 1/2, BEFORE any service is started for real traffic and BEFORE the Cloudflare Tunnel is created in Phase 3**: (1) the mandatory `API_KEY` boot assertion in `lifespan()`; (2) all loopback `127.0.0.1` binds (api 8000, dashboard 5173, caddy 9000); (3) the UID-scoped nftables OUTPUT rule blocking `collab`→loopback app ports; (4) the `ufw` + Hetzner Cloud Firewall inbound-deny rules. The tunnel is the moment the box becomes publicly reachable; opening that path before these four controls are verified would expose financial routes. Phase 2 acceptance therefore includes verifying all four (boot-assertion test, `ss -tlnp` loopback binds, `su collab` curl-denied probe, external `nmap`) and Phase 3 must not begin until they pass.

## 7. Security Considerations

- **OS-user isolation (load-bearing).** Accounting runs as `travis`; the agentic-collab sandbox runs as a **dedicated separate user `collab`** (Prerequisite P-4; BLOCKING). This is the only thing that keeps the DB file (mode 600) and the uvicorn process environment (`/proc/<pid>/environ`, UID-readable) out of the sandbox's reach. If collab ran as `travis`, file perms and `/proc` isolation would both be void.
- **Loopback is host-global.** Binding to `127.0.0.1` is loopback-only but shared across ALL users; any local process (including the sandbox) can connect to `127.0.0.1:8000`/`:5173`. CF Access only guards the tunnel ingress, not loopback. Two defenses:
  - **Mandatory `API_KEY` (code task — Phase 1, VERIFIED in Phase 2 before any tunnel exists).** `accounting/srv` MUST contain a strong random `API_KEY` (`openssl rand -hex 32`, ≥32 chars). Code task in `src/api/main.py`: add a startup assertion in `lifespan()` that raises and refuses to boot when `PLAID_ENV == "production"` and **either `API_KEY` or `INGEST_API_KEY`** is unset or weak (< 32 chars), **or when `API_KEY == INGEST_API_KEY`** (constant-time `hmac.compare_digest`). The equality check MUST be a runtime boot assertion, not merely a one-time deploy check: a future Doppler key rotation that accidentally collapses the two values to the same string would otherwise silently re-merge the dashboard and ingest keys, letting any CF-Access-authorized user who extracts the browser-baked `VITE_API_KEY` from DevTools drive `/api/ingest/*` (arbitrary transaction injection into the tax-of-record ledger). Asserting it at every boot makes the inequality a permanent invariant that survives all rotations. Both keys must be asserted at startup: `require_ingest_api_key` is a FastAPI dependency invoked per-request (not at boot), so without a `lifespan()` assertion a missing `INGEST_API_KEY` would boot silently and then 401 every n8n ingest call — transactions would stop arriving undetected (data-loss-adjacent). `src/api/auth.py:require_api_key` currently no-ops when `API_KEY` is empty — the boot assertion closes that hole at the source for both keys. **Acceptance (Phase 2, BEFORE Phase 3 tunnel):** (1) start `accounting-api` with `PLAID_ENV=production` and an empty/short `API_KEY` and confirm it refuses to boot (journal shows the RuntimeError); (2) start with `PLAID_ENV=production` and an empty `INGEST_API_KEY` and confirm it ALSO refuses to boot (journal RuntimeError); (3) start with two real but EQUAL keys (`API_KEY == INGEST_API_KEY`) and confirm it refuses to boot (journal RuntimeError); (4) then start with two distinct real keys and confirm it boots. This MUST be green before the tunnel is created — not deferred to Phase 5.
  - **UID-scoped local firewall (Phase 2, VERIFIED before tunnel).** Add an `nftables` owner-UID rule denying loopback traffic from the `collab` UID to the app ports. Because `127.0.0.1` traffic from a local process traverses the **OUTPUT** chain on the sending side (an INPUT rule with `--uid-owner`/`skuid` matches **nothing** for loopback — call this out), the rule MUST be on the OUTPUT chain of the `inet` family (covers IPv4 + IPv6):

    ```
    nft add table inet filter
    nft add chain inet filter output '{ type filter hook output priority 0 ; }'
    nft add rule  inet filter output oifname "lo" skuid $(id -u collab) tcp dport { 8000, 5173, 9000 } drop
    ```

    **Persistence (mandatory — the rule is a load-bearing security control and `nft add` is in-kernel-only / lost on reboot).** After the rule is added and verified, persist it: `nft list ruleset > /etc/nftables.conf` and `systemctl enable --now nftables` so `nftables.service` reloads it on every boot. Without this, any Hetzner maintenance reboot or kernel update silently drops the collab→loopback block while services + tunnel restart fine. **Acceptance:** `systemctl is-enabled nftables` returns `enabled`; after a reboot (or `nft list ruleset` re-inspection), the OUTPUT skuid rule is still present and the collab-probe below still fails.

    **Verification (mandatory, Phase 2):** `su -s /bin/sh collab -c "curl --max-time 3 -s -o /dev/null -w '%{http_code}' http://127.0.0.1:8000/api/health/ping"` returns a connection error / timeout / non-200 (NOT 200). Repeat for 5173 and 9000. This is defense-in-depth behind the mandatory `API_KEY`; both must be in place (and the ruleset persisted) before the tunnel.
- **Public exposure (firewall rules land in Phase 1/2, VERIFIED before the Phase 3 tunnel)**: reachability is only via Cloudflare Tunnel + Access; cloudflared is outbound, so **no inbound app ports are opened**. Add explicit **ufw + Hetzner Cloud Firewall** rules denying inbound 8000/5173/9000 from all sources except the Tailscale subnet (Hetzner Cloud Firewall enforces at the hypervisor, robust even if a bind address regresses). Acceptance: `nmap -p 8000,5173,9000 <public-ip>` from outside returns filtered/closed (REQ-HM-003). Tailscale for SSH. These rules MUST be in place and `nmap`-verified before Phase 3 creates the tunnel, so the box never sits publicly reachable with app ports open.
- **`.env` exposure (operator action, pre-cutover, BLOCKING).** A vestigial world-readable `/Users/travis/SGDrive/dev/accounting/.env` contains live `RESEND_API_KEY` (`re_…`) and `STRIPE_RESTRICTED_KEY` (`rk_live_…`). The app uses **Doppler only** (CLAUDE.md rule); the file is vestigial. Pre-cutover: (1) **delete `.env` from the Mac**; (2) **rotate** both the Resend key and the Stripe restricted key (operator); (3) the deploy step MUST exclude it from transfer. The repo→box transfer uses: `rsync -av --exclude='.env' --exclude='.venv' --exclude='node_modules' --exclude='data/' …` (the DB is migrated separately via `.backup`, not rsync of `data/`). Never seed `accounting/srv` from `.env`.
- **Secrets**: Doppler **service token** for headless auth lives in a single canonical root-owned EnvironmentFile **`/etc/accounting/doppler.env`** (`chown root:root`, `chmod 600`, containing one line `DOPPLER_TOKEN=<service-token>`), referenced verbatim as `EnvironmentFile=/etc/accounting/doppler.env` by **every** systemd unit that needs Doppler; `doppler run` then fetches secrets and exec's the process. Tokens never logged. `PLAID_FERNET_KEY` in `accounting/srv` MUST match the key under which the migrated Plaid tokens were encrypted, or decryption fails.
- **VITE_API_KEY in the static build — NOT a second factor against authorized users.** `dashboard/src/lib/api.ts` reads `import.meta.env.VITE_API_KEY`; Vite bakes `VITE_*` vars into the compiled JS at build time. Therefore build with **`doppler run -- npm run build`** (so the value is present — `accounting/srv` carries `VITE_API_KEY` set equal to `API_KEY`, REQ-HM-002; without it the bundle bakes `undefined` and every API call 401s, see the post-build grep acceptance in Phase 1), then **`chmod -R o-r dashboard/build/`**. **Threat-model scope (explicit):** `chmod o-r` only stops the *local* `collab` user from reading the bundle off disk. It does NOT hide the key from browser users — vite serves the bundle through the tunnel, so **any person who passes CF Access (any Google account in the allow-list) can open DevTools and read the baked `VITE_API_KEY` verbatim**. The dashboard `API_KEY` therefore provides confidentiality only against unauthorized *local* processes (collab), NOT against CF-Access-authorized humans. **Requirement:** machine-to-machine callers (n8n ingest) MUST use a **separate, distinct API key** from the one baked into the browser bundle, so a dashboard user who extracts the browser key cannot drive `/api/ingest/*`. `accounting/srv` carries two keys: `API_KEY` (the dashboard/browser key) and a distinct `INGEST_API_KEY` (machine-to-machine, never shipped to the browser; n8n sends it as `X-Api-Key` on ingest calls, see the n8n auth section below). `INGEST_API_KEY` MUST NOT equal `API_KEY`.

  **Concrete enforcement mechanism (code task — Phase 1).** Today `src/api/auth.py:require_api_key` checks only `os.environ.get("API_KEY")`, and `src/api/main.py:163` registers `ingest_router` under the shared `_auth = [Depends(require_api_key)]`. As-is, an n8n caller sending `X-Api-Key: <INGEST_API_KEY>` would get **401** (the app compares against `API_KEY`), so the "two distinct keys" control is unimplementable without a code change. The required change:
  - **`src/api/auth.py` (code task):** add a new dependency `require_ingest_api_key` mirroring `require_api_key` but reading `os.environ.get("INGEST_API_KEY")` (constant-time `hmac.compare_digest`). It checks `INGEST_API_KEY` **only** — it does NOT also accept `API_KEY`. NOTE: because this is a per-request FastAPI dependency (NOT invoked at startup), the non-empty/strength guarantee for `INGEST_API_KEY` is enforced by the `lifespan()` boot assertion in `src/api/main.py` (above), which refuses to boot in production if `INGEST_API_KEY` is unset/weak — the dependency itself just compares.
  - **`src/api/main.py` (code task):** change the `ingest_router` registration from the shared `_auth` to `dependencies=[Depends(require_ingest_api_key)]` (line 163). All other routers keep `_auth` (the browser `API_KEY`).
  - **Do NOT** broaden `require_api_key` to accept either key — that would let a dashboard user who extracted the browser-baked key drive `/api/ingest/*`, defeating the entire separation (the naive-implementation trap).
  - **Acceptance:** `curl -H 'X-Api-Key: <API_KEY>' -X POST https://books.sparkry.ai/api/ingest/run` (with valid CF Access service token) returns **401**; `curl -H 'X-Api-Key: <INGEST_API_KEY>' ...` returns **200**. Also assert `INGEST_API_KEY != API_KEY` in the deploy check.
- **Tax-of-record DB on a shared box**: owned by `travis`, perms 600; systemd hardening uses **`ProtectSystem=strict` + `NoNewPrivileges=yes` + `PrivateTmp=yes`** (NOT `ProtectHome=yes`, which would make the service unable to read its own files under `/home/travis/accounting`). `ReadWritePaths` lists only the real paths each unit must write — **never `/tmp`**: with `PrivateTmp=yes` the unit gets its own private `/tmp` namespace and already has full write access there, so listing the host `/tmp` in `ReadWritePaths` is a contradictory no-op and is removed. `accounting-api` uses `ReadWritePaths=/home/travis/accounting/data` (DB writes only). `accounting-dashboard` (vite preview) uses `ReadWritePaths=/home/travis/accounting/dashboard` because vite writes temp/cache files under the dashboard project dir at preview time. `MemoryMax` per unit (below).
- **Plaid access token**: stays encrypted at rest (Fernet, `PLAID_FERNET_KEY`); only on this box.
- **CF Access × OAuth redirect**: complete the flow WITHOUT a bypass first (the browser redirect carries the Access cookie from the live session); only if it fails, add a narrowly-scoped GET-only bypass for `/admin/connections/oauth-return*`, noting that a bypass risks `oauth_state_id`/`oauth_token` query params landing in edge logs — confirm they are not logged (REQ-HM-008).
- **Machine-to-machine auth through CF Access — n8n → `/api/ingest/run`.** CF Access guards the tunnel for ALL paths. A raw POST from the external n8n host to `https://books.sparkry.ai/api/ingest/run` with no Access credential gets **302'd to the Google OAuth login page and silently fails** (n8n receives an HTML login page, not a 200). The correct mechanism is a **CF Access service token** (client_id + secret), NOT a public bypass. Required design:
  - Create a **CF Access service token** for the n8n caller in Cloudflare Zero Trust.
  - Add a CF Access policy on `books.sparkry.ai` that **accepts that service token only for `/api/ingest/*`** (a service-token policy scoped to the ingest path) — the human Google-OAuth policy continues to guard everything else. **No public bypass.**
  - n8n's HTTP Request node sends three headers: `Cf-Access-Client-Id`, `Cf-Access-Client-Secret` (the service token, satisfies CF Access), plus `X-Api-Key: <INGEST_API_KEY>` (the distinct machine-to-machine key, satisfies the app's `require_api_key`). Store all three in n8n's credential manager.
  - This is also why the ingest key must be **distinct from the browser-baked `API_KEY`** (see the VITE_API_KEY note): a dashboard user who extracts the browser key still cannot drive ingest.
- **External uptime checker → `/api/health/ping` through CF Access.** Same 302 problem: an external monitor (CF cron Worker / healthcheck.io) hitting `books.sparkry.ai` will be redirected to login and report a false outage. **Two coupled decisions:**
  - **Data minimization (code task — Phase 1).** The existing `GET /api/health` (`src/api/routes/health.py:271`) returns a rich `HealthResponse` that includes `failure_log[].error_detail` (the `IngestionLog` model comment states this holds "the full stack trace") plus `plaid_stale_items[].institution_name`/`last_error` (financial-institution names) and `llm_usage` cost estimates. An uptime probe needs none of that. **Code task:** add a new endpoint `GET /api/health/ping` on the health router (`src/api/routes/health.py`) that runs **no DB queries** and returns `{"ok": true}` only. Leave the rich `GET /api/health` in place but move it behind `require_api_key` (it is a dashboard-facing diagnostic, not a public probe) — i.e. relocate the rich health + `source-config` endpoints into the `_auth` group and keep only `/api/health/ping` on the unauthenticated router. **Acceptance:** `curl /api/health/ping` (with CF Access service token) returns `{"ok":true}` and 200 with no `error_detail`/`institution_name`/`llm_usage` keys present in the body.

## 9. Rollback / Disaster Recovery

**Point of no return (PONR):** the first write accepted on the Hetzner box — the **Phase-4 step-10 n8n ingest test** (`/api/ingest/run` persists transactions) — and again at the first Phase-5 `--apply`. The verified R2 baseline (Phase 4 step 9) is taken *before* step 10, so at the instant of PONR a clean offsite copy of the cutover state already exists.

**Rollback decision is BINARY on the PONR — it does NOT depend on any write-detection query.** This is the load-bearing correctness property and it is deliberately query-free:

- **BEFORE the PONR** (no Hetzner write has been accepted — the only writers were unloaded in Phase-4 step 1–2 and the box has not yet run the step-10 ingest test): the box DB is byte-identical to the migrated Mac snapshot (sha256 already proven equal in step 8). **Revert = re-enable the frozen, read-only Mac** against its intact DB. Clean and safe; nothing was lost because nothing was written.
- **AT/AFTER the PONR**: the box has accepted at least one write, so the Mac copy is **known-stale** — reverting to it would silently discard Hetzner-side writes. The design therefore **DEFAULTS TO FORWARD-RECOVERY, ALWAYS. The operator NEVER reverts to the Mac after the PONR.** Forward-recovery means one of: (1) **fix-forward on the box** (correct the fault in place — the box remains the source of truth), or (2) **restore the box from the most recent R2 backup** (the pre-PONR R2 baseline from step 9 plus the daily/on-demand R2 backups together capture all box state; restore the newest good object to the box and resume). Because the decision keys only on "are we before or after the PONR" — a fact the runbook records explicitly at step 10 — correctness is **independent of any SQL write-detector**. There is no branch in which a write-count of zero causes a revert-to-Mac after the PONR.

**`CUTOVER_TS` (diagnostic anchor only):** the single instant recorded at the Phase-4 step-8 gate-pass and stored on the step-9 baseline R2 object's metadata. The box clock is UTC (Phase 1). **It is recorded in SQLite's own storage format** — space-separated `YYYY-MM-DD HH:MM:SS` (UTC), e.g. `date -u +'%Y-%m-%d %H:%M:%S'` → `2026-06-01 14:30:05` — NOT ISO-8601 `...T...Z`, because the app persists `DateTime` columns via `datetime.now(UTC).replace(tzinfo=None)` (`src/models/transaction.py:27`) as space-separated naive strings (`2026-06-01 14:30:05.123456`). A lexical `>` against an ISO-8601 `...T...Z` value would be WRONG: ASCII space (0x20) < `T` (0x54), so every stored row would sort below the cutover and the detector would falsely report zero. The §9 step-2 detector below additionally wraps both sides in `datetime()` so the comparison is format-normalized regardless.

**Write-detection query — DIAGNOSTIC / sanity-log ONLY (not load-bearing).** Now that the decision is binary on the PONR (above), the following query is no longer authoritative; it is run purely to inform the operator and the incident log of *what* changed on the box. It must still be correct so it does not mislead:

**Rollback runbook (numbered):**

2. **(DIAGNOSTIC, non-gating) Survey Hetzner-side writes since `CUTOVER_TS`** — informs the incident report; does NOT choose the branch (step 3/4 is chosen by PONR position alone):

## 11. Risks & Open Questions

- **RAM headroom**: ~1.9 GB working budget on a shared 3.7 GB box; SvelteKit preview + uvicorn + **fpdf2 PDF render (pure Python, no apt deps, ~5 MB resident)** + the agent sandbox must coexist. Always-on ceilings sum to 1088 MB, peaking at 1344 MB when a transient timer fires. Mitigation: concrete `MemoryMax` (§7), journald cap, `--log-level warning`, staggered backup timer (03:17 UTC), monitoring (REQ-HM-014). **Default recommendation (§7): measure OS+collab+Syncthing footprint in Phase 1; if peak free RAM would fall below ~300 MB, resize the box to 8 GB up front rather than running on the edge** — resizing is one-click and the preferred posture for a tax-of-record host, not a last-resort trigger.
- **WAL/OOM:** confirm `PRAGMA journal_mode == wal` after migration; `-wal`/`-shm` are part of the DB and must travel with any manual copy (the cutover uses `.backup`, which produces a single consistent file). The data dir is firmly outside any Syncthing share (REQ-HM-016).
- **Blast radius**: tax-of-record DB shares a host with an agentic sandbox. Mitigation: separate OS user, DB perms, mandatory API_KEY, UID firewall, resource limits (§7).
- **cloudflared reliability**: tunnel is a new always-on dependency; runs under systemd with `Restart=always` + `OnFailure=` alert.
- **vite preview** is a preview tool, not a hardened prod server (same as the Mac today); accepted with `RestartSec`. Future: Caddy `file_server` on `dashboard/build/`.
